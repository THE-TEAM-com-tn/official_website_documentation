## The short version

The rate limits count requests **per visitor**, and the backend recognises a visitor by their
**IP address**. That only works if the server sees each visitor's **own** IP.

On our server it should: nothing was found in front of it (see below), so nothing is configured. Do the
[2-minute check](#check-it-yourself-2-minutes) once to confirm it, and again if you ever put a service
such as Cloudflare in front of `admin.theteam.com.tn`.

## An analogy

Picture a guard at the door of a building who lets each person in **5 times per minute**. The guard
recognises people by their face.

- **Normal case:** every visitor walks in themselves. The guard sees each face and counts each person
  separately.
- **Problem case:** every visitor is driven in by the same taxi driver, and the guard only sees the
  driver's face. After 5 visits, the guard blocks **everyone**, because to them it is the same person.

The guard is the rate limit, the face is the IP address, and the taxi driver is a **proxy**.

## What is a proxy?

A proxy is a server that sits **in front of** our server and passes requests along: Cloudflare (when
its orange "proxied" cloud is on), a CDN or a load balancer. When one is in front, our server sees the
**proxy's IP** on every request instead of the visitor's.

## The two possible setups

| | No proxy in front (our setup) | A proxy in front |
| :-- | :-- | :-- |
| IP the backend sees | The visitor's own IP | The proxy's IP, the same for many visitors |
| Rate limits | Each visitor has their own counter | Visitors share one counter |
| What can go wrong | Nothing | A few login attempts by anyone block the admin login for everyone; busy minutes block the whole site |
| What to do | Nothing | Tell Laravel which proxy to trust, so it reads the visitor's IP from the header the proxy adds |

Telling Laravel to trust a proxy is the `trustProxies` setting in `bootstrap/app.php`. It is
deliberately **not** set today. How to set it up for Cloudflare, step by step:
[Cloudflare and proxies](/security/cloudflare-and-proxies).

## Why not simply turn that setting on?

A proxy passes the visitor's real IP in a header called `X-Forwarded-For`. Anyone can write that
header themselves. If Laravel trusted it without a real proxy in front, an attacker could send a
different fake IP with every request, look like a brand-new visitor each time, and **never hit a
limit**.

So: trust a proxy only when one really exists, and only that proxy.

## Check it yourself (2 minutes)

<Steps>
  <Step title="Sign in to the admin panel from two networks">
    Sign in once from your computer, and once from your phone on **mobile data**, with Wi-Fi off.
  </Step>
  <Step title="Open the Security page">
    In the admin panel, open the user menu and choose **Security**. The **Connected devices** list
    shows the IP address of each signed-in device. (If the list stays empty, the server does not keep
    sessions in the database; ask a developer to check `SESSION_DRIVER`.)
  </Step>
  <Step title="Compare the two IP addresses">
    - **Two different addresses** → the server sees each visitor's own IP. Everything is fine.
    - **The same address on both**, especially `127.0.0.1` or the server's own address → a proxy is in
      front. Ask a developer to configure `trustProxies` for that proxy (see
      [Cloudflare and proxies](/security/cloudflare-and-proxies)).
  </Step>
</Steps>

The backend's responses show no CDN or proxy service in front of the hosting server. That points to

## Before and after deploying

The limits only start working once the new backend code is deployed. Two checks, one before and one
after.

### Before: make sure the server sees real IPs

Do the [2-minute check](#check-it-yourself-2-minutes) **before** deploying the rate limits, or any
change to them.

- **Two different addresses** → go ahead and deploy.
- **The same address on both** → **don't deploy the limits yet.** With a shared address, five login
  attempts by anyone would block the admin login for everyone until the end of that minute, and busy
  moments could block the whole site. First have a developer
  configure the proxy setting (see [Cloudflare and proxies](/security/cloudflare-and-proxies)), then
  repeat the check.

### After: make sure the new limits are live

<Steps>
  <Step title="Clear the old caches">
    On the server, in the backend folder, with the domain's PHP (see [php2shell](/security/php2shell)
    for the exact path):

    ```bash
    php artisan optimize:clear
    php artisan config:cache && php artisan route:cache && php artisan view:cache
    ```

    Without this, Laravel can keep serving the **old** list of routes, with the old limits.
  </Step>
  <Step title="Ask the API twice">
    Run this command **twice in a row**:

    ```bash
    curl -sI https://admin.theteam.com.tn/api/health | grep -i "x-ratelimit"
    ```

    The first run should print something like:

    ```http
    x-ratelimit-limit: 300
    x-ratelimit-remaining: 299
    ```

    and the second run `x-ratelimit-remaining: 298`.
  </Step>
  <Step title="Read the result">
    | You see | What it means |
    | :-- | :-- |
    | `limit: 300`, and `remaining` drops by one each time | The limits are live, and you have your own counter. Done. |
    | No `x-ratelimit` lines at all | The new code is not live yet, or the old caches are still in use. Repeat step 1, then check that the deploy really happened. |
    | `remaining` is already far below 299 on the first run, while nobody else on your network is using the site | You are sharing a counter with other visitors: the server is not seeing visitors' own IPs. Do the 2-minute check. |

    `remaining` can drop by more than one if the site is open in your browser at the same time:
    those requests come from your IP too.
  </Step>
</Steps>

## When to check again

- You turn on Cloudflare's proxy (orange cloud), or any CDN or load balancer, for
  `admin.theteam.com.tn`. Follow [Cloudflare and proxies](/security/cloudflare-and-proxies).
- The backend moves to another host or hosting setup.

In both cases, do the 2-minute check above before relying on the limits.
